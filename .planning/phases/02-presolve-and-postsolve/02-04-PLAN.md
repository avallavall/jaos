<objective>
The activity-range machinery: one routine that computes what a row can reach
given the column boxes, read three ways — the row is forced to an extreme, the
row can never bind, or the row bounds a variable. Then the fixed-point loop that
lets those three cascade, with a round cap that is measured rather than chosen.

Purpose: this is where presolve stops removing structure and starts changing the
feasible region, which is a different class of risk. The checker already
contains a working, swept implementation of exactly this propagation as a
read-only diagnostic; a bound that is slightly too tight there only
under-certifies a dual term, and over-tightening at some propagation intervals
once rejected a correct answer. A presolve bound that is too tight excludes the
true optimum from the region the simplex searches, and nothing downstream is
looking for that. So the rounding direction is conservative by construction, the
tightening is monotone, and the round cap gets the same sweep-with-a-canary
treatment the checker's cap got.

Presolve's tolerances are a third space. The solver's constants are magnitudes
in scaled space and presolve runs before scaling exists; the checker's is a
caller's diagnostic choice for judging a finished answer. Neither converts into
this one. Every constant this plan adds is new, and every one arrives with a
measurement on both sides of it.

Output: three more families, the fixed-point loop, one round-cap constant and
one tightening epsilon, each swept, each written up in `docs/tolerances.md` in
the shape `IMPLIED_ROUNDS` is written up in.
</objective>

  <action>
    Write one routine that computes, for a live row, the minimum and maximum
    activity it can reach given the current column boxes — the sum over the row's
    live entries of the coefficient times whichever column bound that
    coefficient's sign makes extreme, with an infinite bound making that side of
    the range infinite. Accumulate the sum in `long double`, for the reason the
    checker accumulates its activities in `long double`: an activity range is a
    sum of many terms of differing magnitude and the cancellation is real.

    Read that one computation three ways, in this order, because the first two
    are cheaper and remove the row entirely:

    Infeasible: the minimum activity exceeds the row's upper bound, or the
    maximum falls below its lower bound, by more than the tightening epsilon.
    The model has no feasible point; set `JM_PRESOLVE_INFEASIBLE` and stop. No
    column is fixed on this branch.

    Forcing: the minimum activity equals the row's upper bound, or the maximum
    equals its lower bound, within the epsilon. Every live column in the row is
    fixed at the bound that makes it attain that extreme, the row becomes
    redundant and is removed, and one record per fixed column plus one for the
    row goes on the arena.

    Redundant: the whole activity range lies inside the row's bounds. The row can
    never bind and is dropped with no column fixed.

    Bound tightening: otherwise, for each live column in the row, the rest of the
    row's range implies a bound on that column. Take it only when it is strictly
    tighter than the bound the column already carries, by more than the epsilon.
    Only ever tighten, never loosen, and carry a `moved` flag so the round loop
    can tell whether anything happened.

    Round the new bound *away* from tightening by one epsilon rather than toward
    it. This is the asymmetry that matters: the checker's version of this
    propagation is a read-only diagnostic, so a bound that is a shade too tight
    there costs a certification; here it changes the region the simplex searches
    and can exclude the optimum, and nothing downstream would notice. State that
    reasoning in a comment at the rounding site.

    Two boundary cases have to be right and they are one step apart. A tightening
    that lands exactly on the column's opposite bound makes the column fixed —
    the interval collapsed to a point, which is a legitimate reduction and hands
    the column to the fixed-variable rule on the next round. A tightening one
    step past it makes the interval empty, which is infeasibility. Write them as
    two explicit branches with a comment naming which is which; a single
    comparison that decides both is where an off-by-one epsilon turns a solvable
    model into a refused one.

    Replace `02-03`'s exact-comparison placeholder in the singleton-row conflict
    test with the same epsilon, so there is one tightening tolerance in the file
    and not two.

    Declare the epsilon in `src/presolve.c` as a `constexpr double`, named for
    what it decides. Leave its value unset in this task — Task 2 sweeps it, and
    a value written before the sweep is a value the sweep will be tempted to
    confirm. Use a clearly provisional value and a comment saying so, and make
    Task 2's acceptance depend on that comment being replaced by a sweep table.
  </action>
