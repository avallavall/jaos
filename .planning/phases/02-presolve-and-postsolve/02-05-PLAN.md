<objective>
The last three families, and the two most delicate in the set. Duplicate rows,
duplicate columns, and dominated columns.

Purpose: these are the reductions whose predicates are comparisons between
floating-point coefficients, so they are the only ones whose *detection* can be
wrong. The seven families before them either fire on an exact structural
condition — a row has no entries, a column has one — or on an activity range
whose epsilon `02-04` already swept. These three ask whether two coefficients
are in the same ratio, and whether one column is never a worse choice than
another across every row at once. A near-tie that flips the wrong way merges two
rows that are not the same row, or fixes a column that had somewhere better to
be. Neither crashes. Both produce a model that solves, checks and is not the
model the caller loaded.

The literature names dominated columns as the most delicate of the eight, and
warns that a partial-domination check missing one row's sign is a silent
correctness bug rather than a missed opportunity. It goes last, both for that
reason and because by now the D-13 counters have said what the other seven are
worth.

Output: three families, two swept tolerances, three round-trip tests each shown
to reject first, and the near-tie cases built deliberately rather than hoped
absent.
</objective>

  <name>Task 1: Duplicate rows and duplicate columns, and where the equality is decided</name>
  <files>src/presolve.c, src/jaos_internal.h</files>
  <read_first>
    - `.claude/skills/fp-numerics/SKILL.md` section "Tolerances live in a space, and the space is load-bearing", and its guidance to prefer a quantity that has no space at all. The ratio of two coefficients is scale-invariant in a way their difference is not, and that is the whole design of this predicate.
    - `src/presolve.c` after `02-04` — the round loop, the ascending scan order, the arena, and the tightening epsilon as the model for how a presolve constant is declared and commented.
    - `docs/tolerances.md`'s presolve section as `02-04` left it — the shape each new row has to take.
    - `src/model.c` — the CSC arrays and the CSR mirror. A duplicate-row scan wants rows; a duplicate-column scan wants columns; know which of the two the model already maintains before writing a transpose.
  </read_first>
  <action>
    Duplicate rows: two live rows whose nonzero patterns are identical and whose
    coefficients are in a constant ratio. Decide the ratio from the first shared
    entry and then require every other entry to agree with it. Compare the
    ratio, not the difference — the ratio is scale-invariant and an absolute
    difference between coefficients is a quantity whose meaning changes with the
    row's magnitude. The surviving row's bounds become the intersection of its
    own with the other's scaled by the ratio, flipped when the ratio is
    negative. One record restores the removed row's activity and its dual.

    Duplicate columns: the same pattern-and-ratio test on columns, *plus* the
    cost condition — the two costs must be in the same ratio as the
    coefficients. That condition is what keeps this an equivalence rather than a
    dominance. Say so in a comment at the test, and say what happens without it:
    the pair is then a dominance question, which is Task 2's rule or nothing at
    all. The boundary between the two is the specific place an implementation
    goes subtly wrong, so it is stated in the source rather than left to be
    inferred.

    The duplicate-column postsolve record is the only one in the phase that
    produces two primal values from one. The surviving column's bound range
    represents the combined range of the pair, and the replay divides the
    recovered value back between them — the first column takes as much as its
    own bounds allow and the second takes the remainder, or whichever split rule
    the derivation against the checker's sign rule actually requires. Derive it,
    write the derivation as a comment, and let Task 3's test be what decides
    whether the derivation was right.

    Declare the detection tolerance as a `constexpr double` in
    `src/presolve.c`, named for what it decides, applied to the ratio agreement
    and to the cost-ratio agreement. It is a relative tolerance because the
    quantity it judges is already a ratio; state that in the comment. Leave the
    value provisionally set and marked as such — Task 3 sweeps it, and a value
    written before its sweep is a value the sweep is tempted to confirm.

    Scan candidate pairs in ascending index order and require the surviving row
    or column to be the lower index, so the choice of which of a pair survives
    is fixed by construction rather than by whichever the scan reached first.
    Nothing here may depend on an address or on a hash iteration order; if a
    hash is used to bucket candidate patterns, the buckets are walked in
    ascending index order and the hash decides only which pairs are compared,
    never which survives.
  </action>

  <files>src/presolve.c, src/jaos_internal.h</files>
  <read_first>
    - `src/presolve.c` after Task 1 — the duplicate-column predicate, which this rule is the near neighbour of and must not silently absorb.

    - `.claude/skills/jaos-testing/SKILL.md` section "A green result is not a proof" — build the case it must reject.
  </read_first>
  <action>
    A column dominates another when, for every row without exception, its
    coefficient is at least as favourable as the other's, and its cost is no
    worse in minimize-canonical terms. The dominated column can then be pushed
    to its least favourable bound with no loss, because the dominating column
    can substitute for any improvement it might have offered.

    Two properties decide whether this is implemented correctly and both are
    easy to get wrong in a way that compiles.

    First: the condition is universally quantified over rows. A check that
    accumulates a verdict and forgets to reset it per candidate pair, or that
    breaks out of the row loop on the first agreement rather than the first
    disagreement, produces a rule that fires on partial domination. Write the
    loop so that a single disagreeing row rejects the pair, and write a comment
    saying that is what the loop is for.

    Second: the coefficients are compared, so the comparison needs the same
    relative treatment Task 1's ratio needs. Declare a second `constexpr double`
    for the domination comparison rather than reusing the duplicate-detection
    one — they judge different quantities and a shared constant would mean one
    sweep answering two questions. Mark its value not yet swept; Task 3 sweeps
    both.

    Push a `JM_PS_DOMINATED_COL` record carrying the original column index, the
    bound it was pushed to and its cost. The postsolve recovery is the fixed
    value and a reduced cost derived against the checker's sign rule for a
    column resting at that bound — which is not the same obligation as a
    fixed-variable record, because a fixed variable carries no sign condition at
    all and this one does. Write the derivation as a comment and let Task 3's
    negative test decide whether it was right.

    Increment `dominated_col`. This is the eighth and last family; after it every
    field of `jm_presolve_counts` that the phase declared in `02-01` moves on
    some model, and a test should assert exactly that — a declared counter that
    never moves is a family that never fires, and the record would not show the
    difference between that and a family that does not exist.
  </action>
