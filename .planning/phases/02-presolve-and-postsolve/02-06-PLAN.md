<objective>
The review this phase owes itself, run at the only moment it is worth running:
after the code lands and before any campaign.

Purpose: `CLAUDE.md` and the roadmap both require it, and **no GSD workflow
spawns this agent** — the generic code-review capability dispatches a generic
reviewer, not this one. It runs because this plan says so, and phase 1's plans
did not say so. Phase 1's two most valuable findings came from these agents and
from nowhere else, and both arrived after that phase's own gates had already
passed: the cross-check that was blind to a superset bitmap, and a negative
control sitting unused in the committed campaign record showing a 3.0 to 6.4%
improvement on instances the change provably could not speed up.

The defect classes this reviewer is for are exactly the ones this phase is
exposed to. Postsolve's dual and reduced-cost recovery was derived, not verified
— the research that supplied the recipes flagged them as conceptual and not
checked against this codebase's own sign convention. A recovery that is right in
the paper and wrong in this convention produces a plausible answer in the right
shape. Borrowed scratch, reproducibility, tolerance space, and a repair that
hides a residue are the other four, and every one of them has a home in a
1,000-line new module that allocates arenas, compares floating-point ratios and
writes into arrays it did not size.

Output: the reviewer's findings, recorded verbatim, each with a disposition,
and a tree that no longer moves until the campaigns are done with it.
</objective>

    The dual and reduced-cost recovery per family. The formulas were derived

    primal recovery wearing a dual's name.

    model's arrays are all new buffers with a solve-long lifetime, and `sx` has
    its own scratch that presolve now runs beside. Ask whether anything writes
    into a buffer it does not own, or reads one after it has been reused.

    Reproducibility. Nothing may depend on an address, on an allocation order,
    on a hash iteration order or on a clock. The duplicate-detection bucketing
    is the concrete candidate; the survivor-is-the-lower-index rule is the
    claimed defence and the reviewer is the one to say whether it holds.

    scaling exists. Ask whether any comparison in `src/presolve.c` reaches for a
    magnitude that belongs to the solver's scaled space or to the checker's
    caller-supplied one, and whether each new constant's comment states the
    space it lives in.

    A repair that hides a residue. Ask whether any postsolve step clamps,
    rounds or normalises a recovered value in a way that would make a wrong
    recovery pass the checker rather than fail it.

    Give every finding a disposition and write it down. Three are available and
    only three: fixed, with the commit that fixed it; refused, with the reason
    and the measurement or the source that supports the refusal; or carried,
    with what it is waiting on and where it is recorded so it does not vanish.

    A finding is not closed by restating what the code was trying to do. Phase
    1's most useful correction came from an agent refuting three of the stated
    grounds for a verdict the same agent accepted — the verdict survived and
    three of its reasons did not, and both facts were recorded. That is what a
    disposition looks like.

    Where a finding is about a recovery formula, the fix is a test, not an
    argument. Add the case the finding describes to `tests/test_presolve.c`,
    show it failing on the code as it stands, then fix the code. A recovery
    corrected without a test that would have caught it is a recovery that will
    be re-broken by the next person who reads the same paper.

    stop editing. From this commit until `02-07`'s campaigns finish, no file
